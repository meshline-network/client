# Configuration

[Documentation home](../README.md#documentation) · [Command reference](commands.md#configuration-and-diagnostics)

Application settings and account profiles have separate lifecycles. The application configuration is supplied with the program and edited by the operator. A profile is created together with exactly one account by `account create` or `account import`; there is no empty-profile creation command. Both formats currently use `schemaVersion: 1`.

## Application settings

The bundled `config.json` contains:

```json
{
  "schemaVersion": 1,
  "defaultProfile": "default",
  "profilesDirectory": "profiles"
}
```

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Must be `1`. |
| `defaultProfile` | Profile selected when `--profile` is omitted. This name does not create an account. |
| `profilesDirectory` | Absolute path, or a path relative to this configuration file's directory. It is not relative to the working directory. |

The CLI reads this file; it does not generate, migrate, or rewrite it. There is no stored profile list: profiles are resolved under `profilesDirectory`. Output and timeout settings are command-line options, not application configuration fields. Unknown JSON fields are rejected.

## Path resolution

| Input | Resolution |
| --- | --- |
| Explicit `--config PATH` | Use only that file. A relative path is resolved from the calling process's working directory. |
| No `--config` | Read `config.json` beside the running application. No user-directory or working-directory search is performed. |
| `profilesDirectory` | Resolve relative to the selected application configuration file. |
| Profile name | Resolve to `<profilesDirectory>/<name>/profile.json`. |
| Relative file options, such as `--key-file`, `--wallet`, or `--out` | Resolve from the calling process's working directory. |

For a published application, the application directory contains `meshline.exe` or `meshline`. For `dotnet meshline.dll`, it is the DLL's directory. With `dotnet run`, the default configuration therefore lives in the build output directory, not the source directory.

A missing configuration returns `config_missing`; there is no automatic creation or fallback. Copy the bundled file and use `--config` when you need a different location.

## Profiles and account data

A typical profile becomes:

```text
profiles/
└── agent/
    ├── profile.json
    ├── identity.json
    ├── client.db
    ├── session.lock
    └── daemon.log
```

The database is created when an SDK session is initialized. A newly created account can legitimately have no database yet. Lock files, SQLite sidecar files, and the Linux `daemon.sock` appear as needed. `daemon.log` is used by the background process started with `daemon start`.

Profile names contain 1–64 ASCII letters, digits, hyphens, or underscores, beginning with a letter or digit. Windows reserved device names are rejected on both platforms.

| Profile field | Meaning |
| --- | --- |
| `schemaVersion` | Must be `1`. |
| `id` | Generated profile identity; part of the encryption binding. |
| `network` | Network identity in `neo:<network-magic>:<registry-hash>` form; part of the encryption binding. |
| `rpcUrl` | Absolute HTTP(S) RPC URL, without embedded credentials or a fragment. |
| `protection` | The chosen mode and, where applicable, an absolute `keyFile` or a systemd `credentialName`. |
| `protectedKey` | Versioned, protected master-key envelope, generated by the CLI. |
| `dataDirectory` | Optional absolute data path accepted when already present; new profiles keep identity and SDK data beside `profile.json`. |

Do not construct a profile by copying illustrative IDs or ciphertext. Create/import generates the identity, protected key, and manifest together in a private temporary directory, then publishes the completed directory by renaming it. Existing target directories are refused. Normal failure or cancellation removes the temporary profile; abrupt termination may leave `.pending-*` directories, which account listing ignores. An externally generated credential file can remain after failure; inspect it before retrying, and omit `--generate-key` when reusing it.

The identity, network, and key identifiers participate in encryption. Change protection with `secrets rewrap`, not by editing encrypted fields. See [security](security.md#change-protection).

## Select and inspect accounts

With `meshline` on `PATH`, these commands work in PowerShell and Linux shells:

```sh
meshline config show --config ./config.json
meshline account list --config ./config.json
meshline account show --config ./config.json --profile agent
meshline doctor --config ./config.json --profile agent
```

`config show` returns the raw application settings even before any account exists. `account show` returns public identity and resolved profile paths without unlocking secrets or opening an SDK session. `account list` returns all readable local accounts and marks the configured default; it does not require that default to exist. If a profile is damaged, the command returns exit code 3 with readable entries in `error.details.items` and problems in `error.details.issues`.

`doctor` checks configuration and readable account-file structure. Without an explicit profile, an absent default is reported as missing with exit code 0. An explicitly selected missing account, damaged configuration, or failed network check returns a nonzero code and a report in `error.details`. Structural readiness does not prove that credentials unlock. `doctor --network` additionally checks the configured RPC and Registry when a complete profile is available.

The global `--profile` selects a local account. The separate `account profile show/update` command group manages a network nickname, biography, avatar reference, and discovery preference; it does not manage local profile directories.

## Change configuration

Edit `defaultProfile` to change the default selection. Creating another account does not change that field. Use explicit `--profile` when running several accounts or automating commands.

To relocate storage, stop every affected daemon and wait for process exit, move the actual files, then update `profilesDirectory` or the existing `dataDirectory` and credential paths. Editing a path alone does not move data. Keep the generated profile identity and network unchanged. A running daemon retains its startup configuration and must be restarted to pick up changes.

For a program installed in a read-only directory, place a copy of the application configuration and its profiles in a writable location and pass `--config` consistently. Preserve customized configuration during upgrades; the package's default file is not a replacement for your settings. See [backup and restore](operations.md#backup-restore-and-upgrade).
